# Changelog

One entry per podbay plugin version, newest first. Older versions: see `git log`.

## podbay 0.10.3 - 2026-11-27

- Outside reports (owner's decision of 2026-11-27), in a new `reference/outside-reports.md` and a contract section: a report from the client, the team, support or a DM becomes one GitLab issue with one source label (`source::client`, `source::team`, `source::support`, `source::dm`), `bug` or `Feature request`, and a Reporter block. It moves New -> Acknowledged (comment after the reply was sent) -> Triaged (priority and a milestone or `Planned: Backlog`, gate 1) -> optional `Needs Info` (closed as `Resolution: No response` after 14 days, only with a yes) -> the status labels -> closed with one fixed `Resolution:` comment -> `reporter-notified` with a `Notified:` comment. Sessions draft replies and never send them. Steps added to `pb-triage` (2b), `pb-fix` (Needs Info), `pb-orchestrator` (lists stale Needs Info) and `pb-release` step 7 (`Resolution: Fixed in <x.y.z>`, reporter reply drafts, `reporter-notified`).
- Labels must exist; a missing one stops that step and is never created. `pb-guard` needed no change: tests prove it allows these labels and comments and blocks a source label the repo does not have yet.
- Idle sessions, in a new `reference/idle-sessions.md`: the orchestrator stops a worker idle for 30 minutes (`PB_IDLE_MINUTES`), standing roles included, after a check (work pushed, no build or test running, no prompt waiting); a session that fails the check is reported, never stopped. At night every worker that passes stops. Only the orchestrator, the supervisor and a session with an open watch stay up. Resume with `podbay-dev start ... --resume latest`. `pb-kickoff` expects stopped workers.
- `pb-guard` now also scans the file in `-m "$(cat <file>)"` (the kit's form for comments) with `publish-check.sh` and `private-ref-check.sh`; before, only the command text was scanned.
- Round 1 fixes: `pb-triage` closes Duplicate, Won't fix and Cannot reproduce with one comment and a reply draft; Needs Info counts 14 days from its comment; `pb-release` finds outside reports through the `Closes` lines and their `source::` label; the idle check uses `podbay-dev checkouts --all` and `podbay-dev queue`, fails a branch with no upstream, and reads `night:` from `.podbay/orchestrator.md`.
- Private names are no longer in the kit's tests: set `PB_PRIVATE_NAMES` (an ERE) locally and `test-kit-text.sh` checks the skill, reference, template, README and CHANGELOG text for them.
- Tests: test-pb-guard.sh 169 pass (7 new), test-kit-text.sh 259 pass (39 new; 260 with `PB_PRIVATE_NAMES` set).

## podbay 0.10.2 - 2026-11-27

- Ticket status flow (owner's rule of 2026-11-27), in a new contract section "Ticket status": `In Process` when a session starts a ticket (`pb-orchestrator` sets it with the assignee from the `ticket-assignee:` line in `.podbay/orchestrator.md`; the kit names no person), `In Review` when the MR is ready for review (`pb-mr`; a Draft keeps `In Process`), `On Dev` right after the merge into `develop` (`pb-orchestrator`; for an epic, each child ticket when `feat/<epic-name>` merges). The ticket is never closed at `On Dev`: GitLab closes it from `Closes #<n>` when `develop` merges into `main`, and `pb-release` step 7 lists the leftovers and closes them after the user's yes.
- Status label moves and the assignee need no approval; closing an issue still does. The labels must already exist; a missing one stops that step (never created). Briefs from `pb-orchestrator` state the rule.
- `pb-guard` needed no change: tests prove it allows these label moves, the assignee and `glab issue close`, and still blocks a misspelt status label.
- The assignee is added with `--assignee '+<user>'` (a bare name would replace the other assignees). The orchestrator also moves a ticket to `In Review` when it sees a person marked the MR ready, and back to `In Process` when the MR returns to Draft. `pb-fix` sets `In Process` when it starts a ticket without the orchestrator. `pb-release` step 0 checks the default branch is `main` (GitLab closes tickets only on a merge into it), and step 7 also closes epic child tickets, which never auto-close.
- Round 2: batch workers set `In Process` too; starting removes an older status label (`--unlabel 'In Review,On Dev'`); the orchestrator finds an epic's child tickets with `glab mr list --merged --target-branch feat/<epic-name>`; `pb-release --urgent` skips the close step (GitLab closed those tickets on the merge into `main`).
- Role map machine qualifier: a map line may end in ` @<machine>` (`- `~/path` = role @M2`). `pb-role.py` then applies it only on the machine that `podbay-dev setup` names (env `PB_MACHINE` overrides), and it wins over a plain line for the same path. An unknown machine name means qualified lines are ignored; names match exactly. The name is read from `podbay-dev` on PATH, else `~/.local/bin/podbay-dev`, with a 2 s limit that also ends its child processes. `pb-kickoff` takes the qualifier into account. Older kits ignore qualified lines, so release this before a map uses them.
- `pb-orchestrator` briefs carry a fixed line: do not edit `src/ui/kit*`, `src/ui/theme*`, `src/ui/sink.rs` or tokens (only the design-system owner does; a fix that needs a design part stops and asks). It is left out only in a brief to the design-system owner (deliberate: that session owns those files).
- Tests: test-pb-guard.sh 162 pass (7 new), test-kit-text.sh 220 pass (30 new), test-pb-role.sh 35 pass (12 new).
- Review: isolated rounds on Opus. Round 1, no blockers; 5 should-fix (In Review was rarely set, the assignee replaced others, the default-branch assumption, epic children, a 30-label page limit) and the nits fixed. Round 2, no blockers; 4 should-fix (batch workers, older status labels, epic child lookup, `--urgent`) fixed. Round 3, no blockers; 4 should-fix (podbay-dev outside PATH, a hang-safe timeout, `pb-kickoff`, README) fixed; the owner chose no round 4.
- Evals: mr-target, release-develop-flow, kickoff-readback and fix-grill-first all 1.00.

## podbay 0.10.1 - 2026-11-26

- Old label scheme (team decision of 2026-11-26): type `bug`, `feature` or `improvement` (a task, spike or epic gets no type label and starts its description with `Kind: <kind>`); priority `P1`, `P2`, `P3`; the repo's existing `area:<name>` labels; `feature::high` is read, never added. Replaces `type::*`, `priority::*` and `area::*` in the contract, ticket format, pb-triage filing, pb-fix batch mode and follow-ups, the bug checks in pb-mr and pb-fix, and the issue templates.
- `agent-ready` and `needs-human` replace `pb::agent-ready` and `pb::needs-human`. The person-reviewed merge gate is now `human-reviewed` (a new label a person created) in `pb-merge-check.sh`, `pb-tier.sh` and the contract; `needs-human` is never approval.
- Skills never create a label: the filing and batch steps that ran `glab label create` are gone, and a missing state label that batch mode adds (`pb::ready`, `pb::draft`, `pb::skipped`) stops the run before any work. Spikes and epics are found by the triage file's type column or a `Kind:` line, and never get `agent-ready`. `pb-guard` blocks `glab label create|edit|delete`, `glab api` writes to `/labels`, and any label added by `glab issue|mr create|update` (`--label`, `-l`, `-l<x>`) or a `glab api` write (`labels=`, `add_labels=`, also in the query string) that the repo does not have (read with `glab label list`; unreadable -> block), because GitLab creates a missing label silently. It also blocks a session from adding `human-reviewed`: only the person who reviewed adds it.
- Tests: test-pb-guard.sh 155 pass (20 new), test-merge-check.sh 35 pass (2 new: `needs-human` and the old `pb::human-reviewed` do not pass the gate), test-kit-text.sh 190 pass (15 new).

## podbay 0.10.0 - 2026-11-26

- Branch model with `develop` (team decision of 2026-11-26): all work goes into `develop`; `develop` reaches `main` only through the release MR. No more release, hotfix, cherry-pick or sync branches; old `release/*` branches are read-only.
- New `scripts/pb-targets.sh`: the one list of protected branches, sourced by `pb-guard.sh` and `pb-merge-check.sh`. `PB_PERSON_MERGES` is `main master release/*`, so only a person merges there; `develop` is team-shared, so a team member or the orchestrator may merge into it, and adding it to that line makes it person-only. `PB_NO_PUSH` is `main master develop release/*`, so the guard now also blocks a direct push to `develop` and to old release branches (the `PB_KIT_REPO` exception stays for `main` only). When the file is missing, every push and merge is blocked.
- `pb-mr`, `pb-fix`, `pb-triage`, `pb-review`, the batch worker, preflight, the ticket format and the contract work from `origin/develop`, with `develop` as the default target. A Draft MR into `develop` is pushed and opened without asking. Urgent fix: a `hotfix/<short-name>` branch from `main` into `main`, which a person merges, then a `backmerge/main-<yyyy.mm.dd>` MR into `develop` with no squash.
- CHANGELOG between releases: each user-visible MR into `develop` adds its own line under `## [Unreleased]`, and `pb-mr` flags "no CHANGELOG line".
- `pb-release`, with its weekly host:
  - start notice and merged list since the last tag on `develop`, plus a check that `main` has no commits `develop` lacks;
  - `develop`-head health and verify (UI tiers, unchanged);
  - one release-prep MR into `develop`, which turns `[Unreleased]` into the version section and holds the guide, site and version bump;
  - a Draft release MR from `develop` into `main`: a merge commit, no squash, `develop` kept; a person merges it after the team agrees, and it is checked for anything merged after verify;
  - tag and GitLab Release drafts for the person who tags (`tagger:`); the skill never creates, moves or deletes a tag.
  - The freeze template is replaced by `slack-release-start.md`; `release-checklist.md` adds the `host:` and `tagger:` values and drops the sync section.
- Guard: a wildcard or matching refspec (`refs/heads/*`, `:`) is blocked; the value of `-o`/`--push-option` is no longer read as the remote, a `HEAD` or `@` refspec in any position counts as the current branch, `heads/<name>` counts as `<name>`, a bare push at the end of a subshell is checked, and a bare push with a `-C` path the guard cannot resolve is blocked, so these no longer slip a push to `develop` or `main` through.
- Urgent fix: the `hotfix/*` MR bumps the patch version and adds its own CHANGELOG section; the back-merge is merged (never rebased or squashed), reviewed on its own head, and keeps `develop`'s version on a conflict; `pb-release <x.y.z> --urgent <iid>` drafts the tag and deploy hand-off. `pb-release` step 6 repeats the check that `main` has nothing `develop` lacks, so an urgent fix during the release is back-merged before the release MR; step 0 needs the merge method "merge" and squash `never` or `default_off`.
- Tests: test-pb-guard.sh 135 pass (27 new: merge into `develop` allowed, pushes to `develop` and old release branches blocked, wildcard and matching refspecs, push options, `HEAD` and `@` in any position, subshells, unresolvable `-C` paths, the lists, a flipped copy that makes `develop` person-only, and the block-everything fallback without `pb-targets.sh`); test-merge-check.sh 33 pass (2 new); test-kit-text.sh 175 pass (3 old branch-name cases replaced by 59 develop-model cases).
- Evals:
  - new `release-develop-flow`;
  - `mr-target` now covers the `develop` default and the missing CHANGELOG line;
  - `release-notes-stale`, `release-site-stale` and the three review evals now use `develop`.
  - Results: `release-develop-flow` scored 0.00 on 0.9.3 and 1.00 on 0.10.0. All 13 cases score 1.00 on 0.10.0. `mr-target`'s grader was rewritten as a checklist after the judge failed correct answers twice; two runs that timed out at 300 s were rerun.
- Review: 3 isolated rounds on Opus, no blockers.
  - Round 1, 4 should-fix: wildcard and matching refspecs passed the guard, a back-merge could be rebased, step 6 checked against a head that step 2 overwrote, and a release MR that moved after it opened.
  - Round 2, 5 should-fix: a later `HEAD` refspec, the contract still squashing back-merges, squash `default_on`, no version bump or tag path for urgent fixes, and no review for the back-merge head.
  - Round 3, 1 should-fix: step 6 did not repeat the check that `main` has nothing `develop` lacks.
  - All are fixed, along with most nits. Not done: guard blocks for tag pushes and `glab release` (the skill text forbids them); an eval for the urgent route.
