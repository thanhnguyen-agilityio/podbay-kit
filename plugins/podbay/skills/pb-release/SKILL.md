---
name: pb-release
description: Drive the weekly Pod Bay release with its host - merged-MR list on develop, develop-head build and pb-ci, verify (UI tiers), one release-prep MR into develop (CHANGELOG, user guide, website, version bump), the Draft release MR from develop into main, tag and GitLab Release drafts for the person who tags, deploy notes, Slack drafts. Asks for approval before each outward step. Use when the user starts or continues a release. Run as /podbay:pb-release.
argument-hint: <x.y.z> [--from-step <k>] [--dry-run]
---
One release, steps in order. Each step has a check; on a failed check, stop and report what failed and the suggested next step. A release brings `develop` into `main` through one Draft MR. Never merge, push to `main` or `develop`, create, move or delete a tag, create a GitLab Release, run `deploy.sh`, read a signing key, send a Slack message, or run `cargo fmt`/`rustfmt`. The release host (`host:` in `.podbay/release.md`) runs the weekly release and owns its steps; this skill works for the host. Human reference: the team's release playbook (`playbook:` in `.podbay/release.md`). Follow its steps and owners; where this skill and the playbook or the team's working agreements disagree, they win: say where they differ and follow them. Before every outward step (MR, page update), show what will be sent and ask for approval; one approval covers one step. `--dry-run` does every check and draft and sends nothing.

0. **Read** `${CLAUDE_PLUGIN_ROOT}/reference/contract.md`, `${CLAUDE_PLUGIN_ROOT}/reference/release-checklist.md` (project values, rules, formats), `${CLAUDE_PLUGIN_ROOT}/reference/mr-checklist.md` and `.podbay/release.md`. Set `<repo>`, `<id>`, `<checkout>`, `<x.y.z>`, the host and `<prev>` (the newest `v*` tag reachable from `origin/main`; if none, ask). Work in a worktree under the scratchpad. Keep state in `.podbay/release/<x.y.z>/state.md` (step, result, shas, links) and resume from it or from `--from-step`.
1. **Start.** Draft the start notice from `${CLAUDE_PLUGIN_ROOT}/templates/release/slack-release-start.md` into `.podbay/release/<x.y.z>/slack-release-start.md`. List the MRs merged into `develop` since `<prev>`: `glab mr list -R <repo> --merged --target-branch develop --per-page 100` (merged after the `<prev>` tag date) and `git log --first-parent --oneline <prev>..origin/develop`. Check: both lists agree; report any difference. Then `git log --oneline --no-merges origin/develop..origin/main` must be empty: a commit there (an urgent fix) needs its back-merge MR into `develop` first (mr-checklist.md); stop and say so.
2. **Develop-head health.** On the `origin/develop` head, with `CARGO_TARGET_DIR=$HOME/.cache/cargo-target/podbay`: `cargo build --locked`, `cargo test --locked`, `cargo clippy --locked -- -D warnings` (no `--all-targets`). Then `pb-ci` (read `${CLAUDE_PLUGIN_ROOT}/skills/pb-ci/SKILL.md`). Check: all pass, and the log's `PBCI-HEAD sha=` equals the head sha. Record it in `state.md` as the verified head. Repeat this step after every fix merged into `develop` during the release.
3. **Verify.** Run the UI tiers in `${CLAUDE_PLUGIN_ROOT}/skills/pb-verify/references/ui-tiers.md` on the `develop` head from step 2: tiers 1 to 3 yourself, without computer use (tier 2 diffs the screenshots against `<prev>`; tier 3 changes the desktop appearance only after the user agrees), and hand the user, or a computer-use session, only the tier 4 checklist. Hand single tickets to `/podbay:pb-verify`. Check: a Go or No-go verdict with evidence, and the release verify page (`verify:` in `.podbay/release.md`) updated, after approval. No-go stops the release; a blocker is fixed by an MR into `develop`, then steps 2 and 3 run again.
4. **CHANGELOG**, in a new branch `release-prep/<yyyy.mm.dd>` (the release date) from `origin/develop`. Turn `## [Unreleased]` into the `## [<x.y.z>] - <yyyy-mm-dd>` section per release-checklist.md, "CHANGELOG format" (template `${CLAUDE_PLUGIN_ROOT}/templates/release/changelog-section.md`), and add a new empty `## [Unreleased]` above it. Every line must trace to a merged MR from step 1: add the MR link, add a line for a user-visible MR that has none, and remove a line with no merged MR; list the trace (line -> MR) in `state.md`, not in the file.
4b. **User guide**, in the step 4 branch: go through the merged MRs from step 1, and for everything users see, update or add pages in `docs/guide/*.md`. Check that every button, menu and field name matches the app (read the code or a screenshot from step 3). Remove every "Coming in the next release" marker in `docs/guide/` for a feature this release ships (`grep -rni 'next release' docs/guide`); keep a marker only for a feature that is not in `develop`. Rebuild the site as the repo's docs describe and look at the changed pages. If `docs/guide/` does not exist, say so and skip. The guide changes once per release, here, not in feature MRs.
4c. **Website**, in the step 4 branch. If the repo has no `site/`, say so and skip. First, per page, tell hand-written parts apart from parts that `deploy.sh` or the site build fills in (read the build script and the repo's docs; list them in `state.md`); never edit a generated part. Then update the hand-written parts: (a) the release notes page: a new entry for `<x.y.z>` marked Latest (remove the mark from the previous entry), with the known issues from the `### Known issues` group of the step 4 section (or "No known issues." when it has none), and a screenshot of each user-visible change (from step 3 or `pb-verify`; stored where the site keeps its images, never a generated folder); (b) the landing or download page: the "What's new" section, the version on the Download buttons, the installer file names, and feature texts this release changes; (c) hand-written site guide pages the release touches (guide pages built from `docs/guide/` come from the step 4b rebuild; never edit their output). Then run `grep -rnF '<prev without the v>' site/` and explain every hit that stays (a generated part, or history); then `grep -nF '<x.y.z>' <landing page>` must find the new version in each hand-written version spot. Use only design-system parts (contract, Design system first). Check each changed page at phone (390 px) and desktop (1280 px) widths, with screenshots in `.podbay/release/<x.y.z>/site/`. Every text states facts from the merged MRs only.
5. **Version bump**, in the step 4 branch: `version` in `Cargo.toml`; in `Cargo.lock` only the `version` line of the `podbay` package; `python3 tools/licenses/make_credits.py`. Check: `cargo build --locked` and `cargo test --locked credits_match_cargo_lock` pass, and `git diff --stat` shows only `CHANGELOG.md`, `Cargo.toml`, `Cargo.lock`, `assets/credits.json`, `docs/guide/`, the site pages changed in step 4c and the files the site build writes. If the repo has `site/`: a release-prep MR whose hand-written release notes page has no Latest entry for `<x.y.z>` (skip this when step 4c listed that page as generated), or whose landing page does not show `<x.y.z>` in every hand-written version spot (an older version there that step 4c did not explain), is not ready. If the site build stamps the version from `Cargo.toml`, rebuild the site after the bump and run the step 4c greps again. Run `pb-review` on the branch with `--base develop`, then open this one release-prep MR into `develop` through `pb-mr` (from step 2, `--target develop`). A team member, or the orchestrator under the standing rule, merges it.
6. **Release MR**, only after the step 5 MR merged (check with `glab mr view <iid> -R <repo>`). `git fetch`, then rerun step 2 and tier 1 on the new `develop` head. Check: `git log --first-parent --oneline <verified head>..origin/develop` shows only the release-prep MR and release fixes (list each); anything else came in after verify: stop and ask the host whether to rerun step 3 or wait. Write the description: the MR list from step 1, the verify verdict and link, the `<x.y.z>` CHANGELOG section, and the head sha that passed. After approval, open a Draft MR from `develop` into `main`: `glab mr create -R <repo> --source-branch develop --target-branch main --title 'Release <x.y.z>' --description-file <file> --draft`, with no `--squash-before-merge` and no `--remove-source-branch` (a merge commit; `develop` stays). Run `publish-check.sh` and `private-ref-check.sh` on the file first. A person merges it after the team agrees.
7. **Tag and Release hand-off**, only after the user says the release MR merged; check with `glab mr view <iid> -R <repo> --output json` (state merged) and take its `merge_commit_sha`. Check: tag `v<x.y.z>` does not exist (`git ls-remote --tags origin v<x.y.z>`); if it does, stop. Draft, in `.podbay/release/<x.y.z>/tag-and-release.md`, for the person who tags (`tagger:` in `.podbay/release.md`): the annotated tag `v<x.y.z>` on that merge commit with message `Pod Bay <x.y.z>`, and the GitLab Release text: the deploy notes (step 8) on top of the CHANGELOG section, as `{"name": "Pod Bay <x.y.z>", "tag_name": "v<x.y.z>", "description": <text>}`; run `publish-check.sh` and `private-ref-check.sh` on it. The skill never creates, moves or deletes a tag and never creates the GitLab Release; whether a tag is ever moved is the team's decision, made by a person. Build links are added to the Release after the deploy, by a person.
8. **Deploy hand-off.** Draft `--notes` (5 to 8 plain lines plus known issues) from `${CLAUDE_PLUGIN_ROOT}/templates/release/deploy-notes.md` into `.podbay/release/<x.y.z>/deploy-notes.txt`, and the request from `${CLAUDE_PLUGIN_ROOT}/templates/release/slack-released.md`, naming the deploy holder from `.podbay/release.md`. Check: the notes hold only facts from the CHANGELOG section, and, before the request is used, `git ls-remote --tags origin v<x.y.z>` shows the tag on the step 7 merge commit. The deploy holder runs `deploy.sh` from the tag; the skill never does.
9. **Announce.** If the repo has `site/`: after the deploy, open the live landing and release notes pages (from the `downloads:` URL in `.podbay/release.md`) and check that the version, the Download buttons and the installer file names match `<x.y.z>`; report a mismatch to the deploy holder. Then draft the post-deploy message from `${CLAUDE_PLUGIN_ROOT}/templates/release/slack-deployed.md`. Show all drafts in `.podbay/release/<x.y.z>/`. Never send; the playbook says who posts them.
10. **Report.** Per step: result, links (MRs, tag, Release), drafts written, and what is open (who must act next).
