---
name: pb-release
description: Drive the weekly Pod Bay release from freeze to main - merged-MR list, release-head build and pb-ci, verify hand-off, CHANGELOG, user guide, website and version bump MR, tag and GitLab Release, deploy notes, sync MR to main, Slack drafts. Asks for approval before each outward step. Use when the user starts or continues a release. Run as /podbay:pb-release.
argument-hint: <x.y.z> [--branch release/<yyyy.mm.dd>] [--from-step <k>] [--dry-run]
---
One release, steps in order. Each step has a check; on a failed check, stop and report what failed and the suggested next step. Never merge, push to `main` or a `release/*` branch, move or delete a tag, run `deploy.sh`, read a signing key, send a Slack message, or run `cargo fmt`/`rustfmt`. Human reference: the team's release playbook (`playbook:` in `.podbay/release.md`). Follow its steps and owners; where this skill and the playbook or the team's working agreements disagree, they win: say where they differ and follow them. Before every outward step (MR, tag, Release, page update), show what will be sent and ask for approval; one approval covers one step. `--dry-run` does every check and draft and sends nothing.

0. **Read** `${CLAUDE_PLUGIN_ROOT}/reference/contract.md`, `${CLAUDE_PLUGIN_ROOT}/reference/release-checklist.md` (project values, rules, formats), `${CLAUDE_PLUGIN_ROOT}/reference/mr-checklist.md` and `.podbay/release.md`. Set `<repo>`, `<id>`, `<checkout>`, `<x.y.z>`, the release branch (`--branch`, else the newest `origin/release/*`; confirm it) and `<prev>` (the last `v*` tag; if none, ask). Work in a worktree under the scratchpad. Keep state in `.podbay/release/<x.y.z>/state.md` (step, result, shas, links) and resume from it or from `--from-step`.
1. **Freeze.** Draft the cut-off notice from `${CLAUDE_PLUGIN_ROOT}/templates/release/slack-freeze.md` into `.podbay/release/<x.y.z>/slack-freeze.md`. List the MRs merged into the release branch since the cut: `glab mr list -R <repo> --merged --target-branch <release branch> --per-page 100` and `git log --first-parent --oneline <cut point>..origin/<release branch>`, where the cut point is `git merge-base origin/main origin/<release branch>`. Check: both lists agree; report any difference. After the freeze, a blocker is fixed by a hotfix (mr-checklist.md) and ships as a new patch version.
2. **Release-head health.** On the `origin/<release branch>` head, with `CARGO_TARGET_DIR=$HOME/.cache/cargo-target/podbay`: `cargo build --locked`, `cargo test --locked`, `cargo clippy --locked -- -D warnings` (no `--all-targets`). Then `pb-ci` (read `${CLAUDE_PLUGIN_ROOT}/skills/pb-ci/SKILL.md`). Check: all pass, and the log's `PBCI-HEAD sha=` equals the head sha. Repeat this step after every hotfix merge.
3. **Verify.** Hand the head to `/podbay:pb-verify` per ticket, or ask the user to run a desktop computer-use session for the UI click-through. Check: a Go or No-go verdict with evidence, and the release verify page (`verify:` in `.podbay/release.md`) updated, after approval. No-go stops the release.
4. **CHANGELOG.** Write one section from `${CLAUDE_PLUGIN_ROOT}/templates/release/changelog-section.md` per release-checklist.md, "CHANGELOG format". Every line must trace to a merged MR from step 1; list the trace (line -> MR) in `state.md`, not in the file. Remove any `[Unreleased]` section and older cut or hotfix wording for this release.
4b. **User guide**, in the step 4 branch: go through the merged MRs from step 1, and for everything users see, update or add pages in `docs/guide/*.md`. Check that every button, menu and field name matches the app (read the code or a screenshot from step 3). Remove every "Coming in the next release" marker in `docs/guide/` for a feature this release ships (`grep -rni 'next release' docs/guide`); keep a marker only for a feature that is not in the release branch. Rebuild the site as the repo's docs describe and look at the changed pages. If `docs/guide/` does not exist, say so and skip. The guide changes once per release, here, not in feature MRs.
4c. **Website**, in the step 4 branch. If the repo has no `site/`, say so and skip. First, per page, tell hand-written parts apart from parts that `deploy.sh` or the site build fills in (read the build script and the repo's docs; list them in `state.md`); never edit a generated part. Then update the hand-written parts: (a) the release notes page: a new entry for `<x.y.z>` marked Latest (remove the mark from the previous entry), with the known issues from the `### Known issues` group of the step 4 section (or "No known issues." when it has none), and a screenshot of each user-visible change (from step 3 or `pb-verify`; stored where the site keeps its images, never a generated folder); (b) the landing or download page: the "What's new" section, the version on the Download buttons, the installer file names, and feature texts this release changes; (c) hand-written site guide pages the release touches (guide pages built from `docs/guide/` come from the step 4b rebuild; never edit their output). Then run `grep -rnF '<prev without the v>' site/` and explain every hit that stays (a generated part, or history); then `grep -nF '<x.y.z>' <landing page>` must find the new version in each hand-written version spot. Use only design-system parts (contract, Design system first). Check each changed page at phone (390 px) and desktop (1280 px) widths, with screenshots in `.podbay/release/<x.y.z>/site/`. Every text states facts from the merged MRs only.
5. **Version bump**, in the step 4 branch or the next one: `version` in `Cargo.toml`; in `Cargo.lock` only the `version` line of the `podbay` package; `python3 tools/licenses/make_credits.py`. Check: `cargo build --locked` and `cargo test --locked credits_match_cargo_lock` pass, and `git diff --stat` shows only `CHANGELOG.md`, `Cargo.toml`, `Cargo.lock`, `assets/credits.json`, `docs/guide/`, the site pages changed in step 4c and the files the site build writes. If the repo has `site/`: a release MR whose hand-written release notes page has no Latest entry for `<x.y.z>` (skip this when step 4c listed that page as generated), or whose landing page does not show `<x.y.z>` in every hand-written version spot (an older version there that step 4c did not explain), is not ready. If the site build stamps the version from `Cargo.toml`, rebuild the site after the bump and run the step 4c greps again. Run `pb-review` on the branch with `--base <release branch>`, then open a Draft MR into the release branch through `pb-mr` (from step 2, `--target <release branch>`). A person merges.
6. **Tag and Release**, only after the user says the MR merged; check with `glab mr view <iid> -R <repo>` (state merged) and take the head of `origin/<release branch>` after `git fetch`. Check: tag `v<x.y.z>` does not exist (`git ls-remote --tags origin v<x.y.z>`); if it does, stop. Create the annotated tag: `glab api -X POST projects/<id>/repository/tags -f tag_name=v<x.y.z> -f ref=<head sha> -f message='Pod Bay <x.y.z>'`. Put the deploy notes (step 7) on top of the CHANGELOG section in a JSON file `{"name": "Pod Bay <x.y.z>", "tag_name": "v<x.y.z>", "description": <text>}`, run `publish-check.sh` and `private-ref-check.sh` on it, then `glab api -X POST projects/<id>/releases --input <file>`. Build links are added after the deploy (`glab api -X POST projects/<id>/releases/v<x.y.z>/assets/links`), on the user's word.
7. **Deploy hand-off.** Draft `--notes` (5 to 8 plain lines plus known issues) from `${CLAUDE_PLUGIN_ROOT}/templates/release/deploy-notes.md` into `.podbay/release/<x.y.z>/deploy-notes.txt`, and the request from `${CLAUDE_PLUGIN_ROOT}/templates/release/slack-released.md`, naming the deploy holder from `.podbay/release.md`. Check: the notes hold only facts from the CHANGELOG section. The deploy holder runs `deploy.sh` from the tag; the skill never does.
8. **Sync to main.** Follow release-checklist.md, "Sync to main". Check: `git cherry origin/<sync branch> origin/<release branch>` shows no `+` lines except deliberate skips (list each with why); gates and `pb-ci` pass; `pb-review` (Opus) done. Open the MR with `glab mr create --draft --remove-source-branch` and no `--squash-before-merge`, description per mr-checklist.md. A person merges.
9. **Announce.** If the repo has `site/`: after the deploy, open the live landing and release notes pages (from the `downloads:` URL in `.podbay/release.md`) and check that the version, the Download buttons and the installer file names match `<x.y.z>`; report a mismatch to the deploy holder. Then draft the post-deploy message from `${CLAUDE_PLUGIN_ROOT}/templates/release/slack-deployed.md`. Show all drafts in `.podbay/release/<x.y.z>/`. Never send.
10. **Report.** Per step: result, links (MRs, tag, Release), drafts written, and what is open (who must act next).
